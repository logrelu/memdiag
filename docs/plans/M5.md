# M5: detectors on the ledger, then the report

Roadmap row M5, split into three PRs so each stays reviewable:

- **M5a**: ledger-based detectors for `STALE_FACT`, `RECALL_MISS` and `USER_REPAIR`, retrieve/use location,
  and `extract_facts` v2. Branch `m5a-ledger-detectors`.
- **M5b**: `memdiag run` and the HTML report, with each failing turn shown next to its evidence turn.
- **M5c**: constraints and `CONSTRAINT_DROP`, with rule-checkable constraints (length, language, format,
  banned words) first.

## M5a design

### Why not replace the legacy rules?
The legacy rule detectors (`detect.py`) are precise on the attributes they know, and today's metrics are
defined over their assertions. M5a **adds** ledger detectors next to them and merges the two:
- a ledger finding with the same failing turn and normalized key as a legacy finding is a duplicate, and is
  dropped;
- metric definitions change only where the ledger gives a better denominator. The new definitions are written
  so that every failure the legacy rules find is still inside the new denominator. Failures never exceed
  opportunities.

### Detectors (`memdiag/detectors.py`)
- **`STALE_FACT`**: for each assistant turn and each of that user's ledger keys that was updated before the
  turn (it has superseded items):
  - **Opportunity:** the reply mentions any value of the key, old or current. This is a better denominator
    than "rule assertions about an updated attribute", because it counts every place the agent touched the
    updated fact.
  - **Candidate:** the reply mentions an old value and not the current one.
  - **Without a judge**, the candidate is flagged with confidence 0.5. **With a judge**, `check_stale` v1
    asks one specific question: "the user said OLD (quote), then NEW (quote); does this reply use OLD as if it
    were still true?" The judge must quote the reply verbatim, or its answer counts as "no".
- **`RECALL_MISS` (`reask`)**:
  - **Without a judge:** the legacy rule patterns (city, employer, income, credit score) are unchanged.
  - **With a judge:** an assistant turn that asks a question, for a user with live ledger facts, goes to
    `check_reask` v1 with the user's live facts (key = value, plus quote). The judge returns which key is
    asked again and the quote that asks it, and the quote must be verbatim.
  - **Opportunity:** without a judge, turns with a live re-askable fact (unchanged). With a judge, turns with
    any live ledger fact.
- **`USER_REPAIR`** (signal, not a score): the user's next message matches repair phrases ("as I said",
  "I already told you", "like I mentioned", "remember?", "I said ... not ..."). It is placed on the preceding
  assistant turn, with the user's message as evidence, and linked to a ledger key when the repair restates
  that key's value. It counts toward `repair_count` and adds +0.25 confidence (capped at 1) to any memory
  finding on the same turn.
- **`mentions(text, value)`** is deterministic. Numbers match by value (`$140k` matches 140000), and text
  matches as a normalized token sequence.

### Location (L2)
When an assistant event carries `memory`:
- a `STALE_FACT` or `RECALL_MISS` finding gets `location = "use"` if the current value appears in the injected
  memory (the model had it and didn't use it);
- otherwise it gets `location = "retrieve"`.

The same applies to legacy findings with a key. Logs without `memory` get no location.

### extract_facts v2
The ledger passes the people already known for the user ("daughter: Maya") into the prompt, with the rule:
"refer to a known person by their relation". The version is bumped, so the cache cannot mix v1 and v2 answers.

### Entry points
- `run(events, docs=None, judge=None)` builds the ledger and runs both detector sets.
- `memdiag diagnose --model qwen2.5:7b` enables the judge.
- Output gains `"mode": "rules" | "llm"`, `"judge_model"`, and judge usage.

## Metric changes (STABILITY and metrics.md are updated in the same PR)
- `fact_currency`: `STALE_FACT` / (assistant turn, updated key) pairs where the reply mentions any value of
  the key. Every legacy stale assertion mentions the old value, so it stays inside the denominator.
- `recall_continuity`: the denominator widens to any live ledger fact in judge mode, and is unchanged in rules
  mode.
- `memory_faithfulness` and `groundedness` are unchanged: they stay assertion-based. A `STALE_FACT` that only
  the ledger detector found (not a rule assertion) counts in `fact_currency`, not in `memory_faithfulness`.
  This is documented.
- New count: `repair_count`.

## Tests (FakeJudge, no network)
- Stale:
  - old-only mention flagged, mention of both not flagged;
  - judge "no" not flagged, an invented judge quote not flagged;
  - duplicate with a legacy finding merged;
  - failures never exceed opportunities on the demo, MIXED and the fixtures.
- Re-ask:
  - rules mode reproduces the legacy results;
  - judge mode catches "How old is Maya?" when `daughter.age` is live;
  - a judge quote not in the reply is rejected.
- Repair: phrases caught, a normal follow-up not caught, linked to a key, confidence raised.
- Location: memory containing the current value gives `use`, memory without it gives `retrieve`, no memory
  gives `None`.
- extract_facts v2 renders the known people, and the version is bumped.

## Out of scope for M5a
The HTML report (M5b), constraints (M5c), and LLM assertion extraction for `HALLUCINATED_MEMORY`.

## M5b design: `memdiag run` and the findings report

`diagnose` stays as it is, with its strategy replay. `run` is the new primary command, and the report is
built around the localized finding, which is the product (D1).

- **`memdiag run LOG [--model M] [--format F] [--html report.html] [--findings findings.jsonl] [--fail-under ...]`**
  writes findings JSONL (one localized finding per line) and a single-file HTML report, then prints a short
  text summary. It defaults to `report.html` and `findings.jsonl` in the current directory.
- **`memdiag/findings_report.py`** has `findings_html(res, events)`:
  1. A header: users, assistant turns scanned, mode (`rules`, or `llm` with the model name), and date.
  2. Score tiles: every metric with `failures / opportunities`. `n/a` tiles are muted and say why.
  3. "Where memory fails": counts by finding type, and by location (`retrieve` / `use` / not logged).
  4. One card per finding, grouped by user and in turn order. Each card shows:
     - the type, location and confidence;
     - the **evidence turn**, which is the user's earlier message with the quote highlighted;
     - the **failing turn**, which is the assistant reply with the quote highlighted;
     - expected vs got, and the detector and its version.
  5. Signals: user repairs, and pushback no rule explains.
  6. **What this report can't see (D7)**, computed from the run. For example: no memory context was logged,
     so no locations; rules mode only reads N attributes; no deletion requests, so `deletion_compliance` is n/a.
  7. The ledger: each user's facts, with value chains and quotes.
- **Safety:** all log text is HTML-escaped before quotes are highlighted, because a log can contain
  `<script>`. Quotes are verbatim substrings, so highlighting finds them after escaping. The page has no
  scripts, and its only external resource is the Google Fonts stylesheet, with system font fallbacks.
- **Tests:**
  - the report renders the demo and the walkthrough logs;
  - every finding gets a card with both quotes highlighted;
  - `<script>` in a message is escaped;
  - each "can't see" condition appears when it should, and only then;
  - `memdiag run` writes both files, and the gate exit codes work.

## M5c design: instructions the agent drops (`CONSTRAINT_DROP`)

A persistent instruction ("keep answers under 50 words", "reply in Spanish", "no bullet points") is broken
later, while it is still in force. M5c covers only **mechanically checkable** constraints. They need no
model and no judge noise, and they give exact labels for Goal 1's mutation tests. Constraints that need
judgment ("vegetarian recipes only") come later with an LLM check.

- **`memdiag/constraints.py`** (stdlib only):
  - `extract_constraints(text)` reads the user's message for these kinds:
    `max_words`, `max_sentences`, `language`, `bullets`, `no_bullets`, `json_only`, `banned_word`, `no_emoji`
    and `lowercase`. Each comes with its parameter and the verbatim quote.
  - `revocations(text)` catches messages that lift a kind ("you can go longer now", "bullets are fine again",
    "switch back to English").
  - `check(kind, param, reply)` returns pass/fail, what was observed ("83 words") and the offending quote.
- **Scope.** A constraint holds for later assistant turns in the **same session** until it is revoked or
  replaced by a newer constraint of the same kind. Cross-session preferences (procedural memory) are L1 and
  come later.
- **Local override.** When the user's message just before a reply asks for something that conflicts with the
  constraint ("explain in detail" against a word limit, "answer in English" against a language rule), that
  turn is skipped. It is neither an opportunity nor a failure.
- **Language** is identified by stopword counts for en, es, fr, de, it and pt. A reply too short to identify
  is skipped rather than guessed, so it is not an opportunity either.
- **Metric `constraint_retention`**: violated (constraint, reply) pairs / (constraint, reply) pairs in scope.
  `CONSTRAINT_DROP` findings are memory-class. Their evidence turn is the instruction, and the failing quote
  is the offending text.
- **Tests:** about 25 hand-written cases in `tests/fixtures/constraint_cases.json`, covering each kind, pass
  and fail, revocation, replacement, session scope, local override, too-short language, and quote checks.

### M5c review outcome: the standing-instruction rule
A first version read many one-off task requests as standing instructions ("No emojis in my wedding invite",
"Write an essay under 500 words", "Use bullet points for the slides"). Each would then have been checked
against every later reply. That is the most damaging error an eval can make. The rule now is:
- **A standing instruction must be purely about replies.** Either it signals persistence ("from now on",
  "always", "your answers", "keep it"), or nothing but filler is left once the instruction is removed.
- **A task object rejects it:** "in my ...", "for the slides", "to this email".
- **So does a question** without a persistence signal.

Instructions given with a task ("Explain in detail, in under 50 words") apply to that one reply, and are out
of scope until per-turn checks exist. One-off overrides now also cover translation and format requests.
