# M6: Goal 1, mutation testing

Roadmap row M6. Branch `m6-goal1-mutation`, one PR. Goal 1 and its targets are in `docs/ROADMAP.md`.
They were set before this harness existed and are not changed here.

## What is measured
Inject exactly one known memory failure at a known turn into clean conversations, and check whether memdiag
reports it, with the right type, at that turn. Look-alike controls (injected text that is *not* a failure)
measure false positives.

## Data
- **Base:** sessions from LongMemEval-S cleaned (MIT), pinned by sha256
  `d6f21ea9d60a0d56f34a05b609c79c88a451d2ae03597821ea3d5a9678c3a442`. The repo has 17,132 sessions with at
  least 3 user and 3 assistant turns. Each session is truncated to its first 8 turns, and each turn to 600
  characters.
- **Clean bases only.** A session is a base only if memdiag finds nothing in it (rules mode). The fraction
  rejected is reported as the **background finding rate**. These are not counted as false positives, because
  some may be real failures in the generated chats. They are not counted as recall either.
- The suite is regenerated deterministically (seeded) from the pinned file. The suite file is git-ignored;
  the generator and the results are committed.

## Case kinds
Each case is one user's log, built from 1 to 3 base sessions, with one injection.

| Type | Injection | Gold failing turn |
|---|---|---|
| `STALE_FACT` | session 1: the user states a fact; session 2: the user updates it; session 3: an assistant reply asserts the old value | that reply |
| `RECALL_MISS` | session 1: the user states a fact; session 2: an assistant reply asks for it again | that reply |
| `CONSTRAINT_DROP` | the user gives a standing instruction; replies before the target are made to comply; the target breaks it | the target reply |
| `USER_REPAIR` | the user's next message repeats or corrects ("I already told you") | the assistant turn before it |

Facts cover rule attributes (city, employer) and LLM-only attributes (a family member's age), so rules mode
and LLM mode can be compared by attribute group.

**Controls** use the same scaffolding with a non-failure:
- the reply uses the *current* value, or mentions both ("you moved from A to B");
- a question about something unrelated ("How old is your car?");
- an instruction revoked or overridden before the long reply;
- a thankful follow-up instead of a repair.

A control counts as a false positive if memdiag reports the control's type anywhere in the case.

## Splits (D12: tune on dev only)
- Every phrasing template has an id and is tagged `dev` or `heldout`, about 70/30. Sessions are split 70/30
  by a hash of the session id.
- **Held-out cases use held-out templates and held-out sessions.** The headline numbers come only from
  held-out cases.
- Detectors may be tuned on dev results only. Tuning that changes held-out numbers is reported as a new run,
  not as a replacement for the old one.

## Scoring (RankJudge-style strict credit)
- **Detection recall:** the case has a finding of the gold type anywhere.
- **Exact-turn accuracy:** a finding of the gold type at the gold failing turn, out of all positive cases.
- **False-positive rate:** controls with a finding of their type, out of all controls.
- Each is reported per type, per attribute group, per split, and per mode (`rules`, `llm`), with Wilson 95%
  confidence intervals and the counts.
- **Flip rate (LLM mode):** 3 uncached reruns on a held-out sample, counting the cases whose verdict changes.

## Targets (pre-registered in the roadmap)
On held-out cases:
- recall ≥ 0.85 per shipped type;
- exact-turn ≥ 0.80;
- false-positive rate ≤ 0.05;
- flip rate ≤ 5%.

A miss is published with its number.

## Known threats to validity (stated in `docs/validation.md`)
- **Templates are short and explicit.** Real failures are subtler, so these numbers are an upper bound on
  real-log recall. External validity is Goal 2 (M7).
- **Some phrasings overlap with the detector rules.** Held-out templates were written to include phrasings
  the rules don't cover. Held-out recall in rules mode shows how much the rules generalize.
- **One model plays every role in LLM mode.** That holds until a second judge family is run.

## Deliverables
- `validation/goal1/templates.py`: phrasing pools with ids and splits.
- `validation/goal1/mutate.py`: base selection, injection, controls and the suite JSONL.
- `validation/goal1/score.py`: runs memdiag on each case and writes `validation/results/goal1_<mode>.json`.
- `validation/goal1/report.py`: generates `docs/validation.md` from the results.
- A single command, `python -m validation.goal1 --mode rules` (or `--mode llm --model qwen2.5:7b --limit N`),
  runs all of the above.
- Tests on tiny hand-written base sessions, with no dataset and no model. They check that injection places
  the gold turn correctly, that controls contain no failure, and that scoring counts exact-turn hits.

## Results (2026-11-13) and diagnosis
Full tables: `docs/validation.md`.
- **Rules mode, all 200 held-out cases.** Recall 0.60: 1.00 for `CONSTRAINT_DROP` and `USER_REPAIR`, 0.16 for
  `STALE_FACT`, and 0.24 for `RECALL_MISS`. False positives 0/100. On dev the same rules score 0.92, so the fact
  rules don't generalize to unseen phrasings. They were not tuned on held-out.
- **LLM mode (`qwen2.5:7b`), 64 held-out cases** (8 positives and 8 controls per type). Recall 0.88 (28/32,
  CI 0.72-0.95), false positives 0/32. By type: `RECALL_MISS` 0.88, `CONSTRAINT_DROP` 1.00 and `USER_REPAIR` 1.00
  meet the target; `STALE_FACT` 0.62 (5/8) does not.
- **Goal 1 is not met yet.** Three things fall short:
  - the per-type target fails for `STALE_FACT`;
  - n = 8 per type in LLM mode gives wide intervals;
  - the flip rate has not been run.
- **Diagnosis of the 3 `STALE_FACT` misses** (read from cached outputs, no tuning). All three are held-out
  city cases with the update "We packed up and settled in X last week". In each one the ledger had the update
  right (for example `user.city: Portland -> Atlanta`), and the mention check produced the candidate. The 7B
  `check_stale` judge then answered `uses_old: false` for an explicit stale reply ("Near you in Portland, there
  are good options"). This is the same failure mode as the earlier re-ask miss: the judge has false negatives.

## Next (each change validated on dev first, reported as a new run next to this one)
1. **Judge policy for stale candidates.** Options:
   - keep a rejected candidate as a low-confidence finding instead of dropping it;
   - run a second judge family or a larger model and compare.

   The suite's controls never produce stale candidates, so they can't show what the judge's veto buys in
   precision on real logs. That decision needs Goal 2 data.
2. **The full LLM held-out run** (25 per type) and the flip rate (3 uncached reruns) for tighter intervals.
3. **Goal 2 (M7):** real labels and human agreement.
